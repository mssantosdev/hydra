Managing worktrees, made easy and powerful.Gerenciar worktrees, de forma fácil e poderosa.

Easy is that you stop handling paths. Name a repo and a branch from anywhere in the workspace — hydra places the worktree, registers it, and every other command finds it without you tracking anything. Powerful is what that registration buys: one name addresses a set of worktrees across repositories, so you create them, run across them, sync and remove them as one — and hydra list -o json piped into hydra apply - rebuilds the whole workspace somewhere else. It never merges, never rebases, never resolves a conflict, and never talks to a forge.Fácil é você parar de lidar com caminhos. Diga um repo e uma branch de qualquer lugar do workspace — o hydra cria o worktree, registra, e todos os outros comandos acham sem você rastrear nada. Poderoso é o que esse registro compra: um nome endereça um conjunto de worktrees em vários repositórios, então você cria, executa, sincroniza e remove tudo de uma vez — e hydra list -o json com pipe para hydra apply - reconstrói o workspace inteiro em outro lugar. Nunca faz merge, nunca faz rebase, nunca resolve conflito e nunca fala com um forge.

§ 03

The modelO modelo

project → group → repo → worktreeprojeto → grupo → repo → worktree

Four nouns say where files live. The fifth is the work itself — the one that spans repos. Git data lives once, in a bare repository under .bare/. Every worktree is a plain directory you can cd into.Quatro substantivos dizem onde os arquivos ficam. O quinto é o próprio trabalho — o que atravessa repos. Os dados do git ficam uma vez, em um repositório bare em .bare/. Cada worktree é um diretório simples no qual você pode dar cd.

shop/ # project — one workspace ├── .hydra/ │ ├── config.yaml # the manifest (schema 3) │ └── state.yaml # topic membership, under flock ├── .bare/ │ ├── checkout-api.git # git data, once per repo │ └── storefront-web.git └── services/ # group — a category you choose ├── checkout-api/ # worktree: repo + branch ├── checkout-api-stage/ └── checkout-api-feat-split-tender/ ← topic PAY-4417

A topic is a name you give a piece of work, plus the record of which worktrees belong to it. Name it once and status, run, start and remove act on the whole set. That membership is written down, never inferred from a branch name — feat/x in one repo and feat/x in another stay unrelated until you say otherwise, so a command can't act on a set you didn't mean. Worktrees without a topic are normal, and hydra topic attach links work you already started — no migration step.Um tópico é um nome que você dá a um trabalho, mais o registro de quais worktrees pertencem a ele. Nomeie uma vez e status, run, start e remove agem no conjunto inteiro. Essa associação é registrada, nunca deduzida do nome da branch — feat/x em um repo e feat/x em outro seguem sem relação até você dizer o contrário, então um comando não age num conjunto que você não quis. Worktrees sem tópico são normais, e hydra topic attach vincula trabalho que você já começou — sem etapa de migração.

no guessing from branch namessem adivinhar pelos nomes das branches

Membership is recorded, never inferred. hydra will not parse feat/PAY-4417-split and guess. That is what makes acting on the whole set possible. Branch naming is a team convention; a tool that guesses is wrong the day the convention changes.A associação é registrada, nunca inferida. O hydra não vai analisar feat/PAY-4417-split e adivinhar. É isso que permite agir no conjunto inteiro. Nomear branches é convenção de equipe; uma ferramenta que adivinha erra no dia em que a convenção muda.

§ 06

A unit of workUma unidade de trabalho

start, topic, runstart, topic, run

One piece of work, several repositories, one command. The topic id is whatever you already use — a ticket number, an incident, a name you invented. It's just a string; hydra never contacts a tracker. It builds the work out of worktrees and keeps the set together.Um trabalho, vários repositórios, um comando. O id do tópico é o que você já usa — um número de ticket, um incidente, um nome que você inventou. É só uma string; o hydra nunca fala com um tracker. Ele monta o trabalho a partir de worktrees e mantém o conjunto junto.

Work does not form a tree, so topics relate as a graph. Two relationships mean something to hydra: part_of is containment, and depends_on is a peer that must land first. Any other kind must be dot-namespaced — acme.tested-by — and hydra stores and reports those while gating on nothing in them, so your own tooling builds on the same primitive. meta is free-form key/value data hydra never interprets.O trabalho não forma uma árvore, então tópicos se relacionam como um grafo. Duas relações significam algo para o hydra: part_of é contenção, e depends_on é um par que precisa entrar primeiro. Qualquer outro tipo precisa de namespace com ponto — acme.tested-by — e o hydra armazena e reporta esses sem impor nada sobre eles, então sua ferramenta constrói sobre a mesma primitiva. meta é dado chave/valor livre que o hydra nunca interpreta.

hydra topic close is the gate, and it derives rather than trusts: a part_of child must be closed and its branches must have reached this topic's branch in the same repository, which git is asked on every call. A depends_on target only has to be closed — peers share no integration branch, so merged-ness is not checkable and is not pretended. Every refusal names its own override in next[], and --force closes anyway while still reporting what it overrode, at exit 0.hydra topic close é o portão, e ele deriva em vez de confiar: um filho part_of precisa estar fechado e seus branches precisam ter alcançado o branch deste tópico no mesmo repositório, o que é perguntado ao git em cada chamada. Um alvo depends_on só precisa estar fechado — pares não compartilham branch de integração, então merge não é verificável e não é fingido. Toda recusa nomeia seu próprio override em next[], e --force fecha mesmo assim, ainda reportando o que sobrepôs, com saída 0.

Then act on the whole topic at once. Everything after -- goes straight to exec — no implicit shell, so no quoting surprises. Pass -- sh -c '…' when you want a shell.Depois atue no tópico inteiro de uma vez. Tudo após -- vai direto ao exec — sem shell implícito, então sem surpresas de aspas. Passe -- sh -c '…' quando quiser um shell.

Filters combine: --topic, --repos, --group, --all and --filter dirty|behind|branch:<glob> narrow together instead of overriding each other. A filter that matches nothing returns empty, not everything.Filtros combinam: --topic, --repos, --group, --all e --filter dirty|behind|branch:<glob> restringem juntos em vez de se sobrescrever. Um filtro sem match retorna vazio, não tudo.

RecoveryRecuperação

A manifest can also declare the branches each repo keeps checked out, which is what makes it enough on its own. repo add --branches records them, repo set changes them later, and repo restore creates them.Um manifesto também pode declarar as branches que cada repo mantém, o que é o que o torna suficiente por si só. repo add --branches registra, repo set altera depois, e repo restore cria.

That is the difference between the two artifacts. The manifest is the shape you declared, and it never contains work in progress — nothing but repo add --branches and repo set writes it. A captured list --output json is what one machine currently has, topics included; apply replays that. Structure, not secrets: a restored workspace has every tracked file and none of the ignored ones, so carry: in the manifest names the ones a worktree needs anyway — a .env, a dev certificate — and hydra places them on creation.É essa a diferença entre os dois artefatos. O manifesto é a forma que você declarou, e nunca contém trabalho em andamento — nada além de repo add --branches e repo set escreve nele. Um list --output json capturado é o que uma máquina tem agora, tópicos incluídos; apply reproduz isso. Estrutura, não segredos: um workspace restaurado tem todos os arquivos versionados e nenhum dos ignorados, então carry: no manifesto nomeia os que um worktree precisa de todo jeito — um .env, um certificado de dev — e o hydra os coloca na criação.

Seven registered names: terminal, hydra, tokyonight, catppuccin, dracula, nord, onedark. terminal is the default because every colour is an ANSI slot and no background is painted, so hydra inherits the palette you already configured; that works over SSH and in tmux and follows a live theme change. hydra config set theme hydra selects the first-party palette. contrib/ghostty/hydra and contrib/omp/hydra.json are generated from it by scripts/gen-themes.py for the reverse direction.Sete nomes registrados: terminal, hydra, tokyonight, catppuccin, dracula, nord, onedark. terminal é o padrão porque cada cor é um slot ANSI e nenhum fundo é pintado, então o hydra herda a paleta que você já configurou; funciona via SSH e em tmux e segue uma troca de tema ao vivo. hydra config set theme hydra seleciona a paleta própria. contrib/ghostty/hydra e contrib/omp/hydra.json são gerados a partir dela por scripts/gen-themes.py na direção inversa.

HooksHooks

Declarative shell commands at lifecycle events: post_clone, post_add, pre_remove, post_remove, post_sync, and four that fire once per topic operation: post_topic_start, pre_topic_close, post_topic_close, pre_topic_remove. A failing hook never deletes a correctly created worktree.Comandos shell declarativos em eventos do ciclo de vida: post_clone, post_add, pre_remove, post_remove, post_sync, e quatro que disparam uma vez por operação de tópico: post_topic_start, pre_topic_close, post_topic_close, pre_topic_remove. Um hook com falha nunca remove um worktree criado corretamente.

Each hook receives:Cada hook recebe: HYDRA_EVENT, HYDRA_PROJECT, HYDRA_PROJECT_ROOT, HYDRA_GROUP, HYDRA_REPO, HYDRA_BRANCH, HYDRA_WORKTREE_PATH, HYDRA_BARE_PATH, HYDRA_TOPIC, HYDRA_SOURCE_WORKTREE. The last two are empty when there is no topic or no originating worktree, and always exported so a hook under set -u can test them. hydra hooks ls --output json publishes this list, so it never has to be read off a page.Os dois últimos ficam vazios quando não há tópico ou worktree de origem, e são sempre exportados para um hook sob set -u poder testá-los. hydra hooks ls --output json publica esta lista, então ela nunca precisa ser lida de uma página.

Every hook is bounded: timeout: per hook, ten minutes by default, 0 to disable. Hooks were the one unbounded wait in hydra, so one that hung hung the tool — worst on a machine bootstrap, whose own deadline is minutes.Todo hook é limitado: timeout: por hook, dez minutos por padrão, 0 para desativar. Hooks eram a única espera sem limite no hydra, então um que travava travava a ferramenta — pior num bootstrap de máquina, cujo prazo é medido em minutos.

hydra hooks ls lists configured hooks; hydra hooks run <event> runs one manually. Pass --no-hooks on any command to skip them all.hydra hooks ls lista os hooks configurados; hydra hooks run <event> executa um manualmente. Passe --no-hooks em qualquer comando para ignorar todos.
